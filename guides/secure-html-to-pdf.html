SECURITY · DEVELOPER GUIDE

How to render HTML to PDF safely in a SaaS backend

When your app turns HTML into a PDF, you’re also running a browser inside your infrastructure. That’s useful, but it deserves care. Here are practical ways to limit what the browser can do—and an honest look at what Vervant has and hasn’t verified yet.

Start with the threat model

When a backend accepts HTML from users, templates or integrations, the renderer may process attacker-controlled markup. A browser that can execute scripts or fetch arbitrary URLs can turn a PDF endpoint into a route toward internal services, metadata endpoints, local files or unexpected third-party requests.

1. Disable page JavaScript

Most invoices and reports work perfectly well with static HTML and CSS. Keep page JavaScript off unless you have a clear, tested reason to need it. It’s a helpful safeguard, but it doesn’t replace OS or container isolation.

2. Block outbound and local network requests

A good starting point is to block browser requests by default, either with request interception or a network policy. Redirects, IPv6 and DNS rebinding deserve attention too. It’s safer to start with “nothing gets through” than to maintain a list of addresses you hope to block.

3. Isolate the renderer

Give Chrome its own tightly restricted container or worker. Keep application secrets, SSH keys, source code and writable host folders out of its reach. Keep the browser updated, and leave its own sandbox enabled whenever the hosting environment supports it.

4. Enforce resource limits

Set maximum HTML size, request duration, page count, memory and concurrency. Rate-limit by user and API key. Reserve monthly quota atomically so parallel requests cannot exceed plan limits, and release the reservation if rendering fails.

5. Avoid leaking document data

Do not log full HTML, customer records or PDF contents by default. Log request IDs, account IDs, execution times, page counts and safe error categories. Define retention and deletion policies before accepting customer data.

6. Be precise about “secure”

Disabling JavaScript and remote requests reduces attack surface; it does not make an application automatically secure. Document runtime isolation, dependencies, limits, storage, retention and incident response. Never claim a certification you have not earned.

Vervant's current approach

In the local prototype, page scripts are disabled and browser requests are intercepted. Chromium now runs inside an outer Bubblewrap boundary with separate user, network, process, IPC and UTS namespaces, fewer capabilities, a read-only root filesystem, hidden application data and a temporary browser profile. A local test confirms that it cannot reach a service on the host’s localhost address. The production Docker image now passes its PDF and network-isolation smoke test in GitHub Actions. The disposable CI container receives explicit namespace permissions so Bubblewrap can start; this is not a production deployment or proof that every managed host supports the same setup. Railway has confirmed that standard services do not expose the required seccomp/AppArmor controls, so it is not a compatible hosting target for this renderer. We’re keeping the hosted API offline until a VM or managed runtime that supports the required namespaces has been tested. Chromium’s own --no-sandbox flag remains enabled inside the outer boundary because its nested sandbox does not start in this environment. This prototype has not been independently audited or certified. Please don’t send personal, confidential or production documents.
