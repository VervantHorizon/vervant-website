HTML to PDF in Node.js with Puppeteer

Puppeteer gives your Node.js app control over Chromium’s print engine. Getting a first PDF is simple; running the browser safely and reliably takes a little more care.

A minimal example

import puppeteer from 'puppeteer';

const browser = await puppeteer.launch({ headless: true });
try {
  const page = await browser.newPage();
  await page.setJavaScriptEnabled(false);
  await page.setContent(html, { waitUntil: 'load', timeout: 10000 });
  const pdf = await page.pdf({
    format: 'A4',
    printBackground: true,
    preferCSSPageSize: true
  });
  return pdf;
} finally {
  await browser.close();
}

This starter is intentionally small. Before using it with HTML you don’t fully trust, block browser requests by default and run Chromium inside a properly isolated container. A working PDF is only the first step.

Use print CSS

@page { size: A4; margin: 18mm 14mm; }
@media print {
  .no-print { display: none !important; }
  .page-break { break-before: page; }
  tr { break-inside: avoid; }
}

Manage browser lifecycle

Starting Chromium for every request is easy to understand, but it can get expensive. Reusing a browser can be faster, though it also means you need to think about clean-up and isolation between jobs. Put limits on parallel pages, recycle workers and keep an eye on memory.

Control external resources

Remote images, fonts and stylesheets can change the final PDF and give the browser a route out to the network. Bundled, reviewed assets are easier to control. When remote files are truly needed, fetch them through a separate service that checks the source, file size, type and redirects.

When should you use a PDF API?

There isn’t one right answer. Self-host Puppeteer when rendering is core to your product and your team is happy to maintain browsers, security controls and scaling. A hosted API may be simpler when you just need a dependable document endpoint. Compare data retention, region, access controls, quotas and total cost before choosing.
